## Inter-Process Communication (IPC)
When 2 or more processes want to co-ordinate or exchange information, the mechanism for doing so is called *inter-process communication*, usually just simply abbreviated as IPC. If a process shares data with another process in the system, the OS will also provide facilities to make this possible.

Some basic terminology that is needed is that the data being transferred is typically referred to as the *message*, while the process sending that message is the *sender*. The one receiving the message is the *receiver*.

Also obviously, all communicants need to agree on some sort of standard when transferring the data. How this agreement is reached is outside the purview of the OS, however most people agree on publishing a standard online and then just simply following it.

There are 2 types of sending and receiving, async, and sync. As is obvious:

It is also common for the async receive case to send back another message acknowledging the receipt of the message.

A general paradigm for understanding IPC is known as the *producer-consumer* problem. This is when the producer creates some information which is later used by the consumer. For example, the database may produce the data (some records from the database) to be consumed by the shell to be displayed to the user. This is a general problem and applicable to client-server situations.

There are 3 approaches we will consider on how to accomplish IPC.
1. The file system
2. Message passing
3. Shared memory
All of these are common and a system can easily implement them all. There is no single option that is optimal in every situation, but each have areas of both strength and weakness.

### File System
One way for 2 processes to communicate is through the file system. Messages stored in the file system could be presisten and survive a reboot. It can also be used when both the sender and receiver know nothing about each other.

They can both agree to write and read at a specific path/location. We do have to make sure we don't overwrite anything but we can often get around this by using multiple files with unique IDs.
### Message Passing
Message passing is a service provided by the OS, where the sending will give the message to the OS and ask that it be delivered to a recipient. THere are 2 basic operations, both sending and receiving.

## Using Signals
Signals do not contain a message, it's more just an announcement or alert/alarm.

This does mean that it can't be used for all IPC scenarios but can still be used for some of them. Enums are located in the `signal.h` file for e.g. SIGKILL.

We already learned how to send a signal from the command line. However, there are 2 functions for sending a signal programmatically.

```c
int kill(int pid, int signo);
int raise(int signo);
```

Both functions will return 0 if they were successful and -1 if they fail. The raise function sends the signal back to the current process.

We need to know the PID of the recipient which is fine but this requires a little negotiation for how the processes find out about each other. A common convention is for services to register themselves in some way, which might be as simple as putting a file on disk in a specific location that contains the PID.

We can use `kill` to do some interesting things, like signal all your processes. It depends on the value chosen for your *pid* argument.

We can also just invoke kill with 0 which means the null signal. It doesn't send anything but can be used to check if the recipient process exists.x

A signal can be sent to a given process, but that process can only actually deal with it when that process is running. A signal can be generated by something and is later delivered to the recipient. But during the time between generation and delivery we say the signal is *pending* the Pending signal is then delivered as the first opportunity

Interestingly, for most, but not all signals. Your process can just refuse to listen. This is called blocking signals and be done for everything except `SIGKILL` and `SIGSTOP`.

Signals also have a default action, this is called the disposition of the signal. But if you don't explicitly change what happens when the signal arrives, the default happens, however we can change it. Either we ignore it, run a signal handler, and run the default action.

```c
void (*signal(int signo, void (*handler)(int))) (int);
```

This is difficult to read but it's actually just pretty simple, you can just do

```c
void sig_handler(int signal_num) {
	// Handle the signal in some way
}
```

We can only use functions that are *reentrant*. That is to say, a function that can be interrupted during execution, have another complete call to the same function execute, and then finally resume. In particular the big ones to avoid are, printf, malloc, and free. All of these could possibly block the process of reading a file or something similar.

There are tables of what functions are safe to invoke from within a signal handler. In general what you are looking for is a designation of async signal safe.

To block a signal, unblock one or just find out what the current state is, the function is.

